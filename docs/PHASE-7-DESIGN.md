# تصميم المرحلة 7 — استقبال الأفكار وفرزها

## الهدف

تفتح المرحلة 7 قناة عامة من GitHub Issue Forms لاستقبال أفكار منتجات مصغرة باللغة العربية، ثم تعالج كل فكرة آليًا بطريقة حتمية قابلة للمراجعة. الناتج هو تعليق واضح وتصنيف للحالة واقتراح backlog عند اجتياز الفحص. لا يُعد الناتج موافقة على البناء، ولا يُعدّل `ideas/backlog.json`، ولا ينشر منتجًا.

## قناة الاستقبال

يستخدم النموذج `.github/ISSUE_TEMPLATE/product-idea.yml`. يطلب عنوان الفكرة، المشكلة، وصف المنتج، الجمهور، الشكل التقريبي، دليل الحاجة، القيود الاختيارية، وإقرارين صريحين بأن القضية عامة ولا تحتوي أسرارًا أو بيانات شخصية أو بيانات عملاء. تبقى القضايا الفارغة مسموحة للمشكلات التقنية القديمة، لكن Workflow المرحلة 7 يعالج فقط القضايا التي تحمل `idea:submitted` أو قضية يحددها التشغيل اليدوي.

## الحالات

| الحالة | المعنى | إجراء المراجع |
|---|---|---|
| `ready-for-review` | اجتازت الفحوص ولا تبدو مكررة | مراجعة بشرية ثم نسخ الاقتراح إلى backlog يدويًا عند القبول |
| `needs-info` | حقل مطلوب مفقود أو قصير | طلب معلومات إضافية من صاحب القضية |
| `duplicate` | تشابه قوي مع فكرة موجودة | مراجعة الفكرة المرجعية وإغلاق التكرار أو إبقاؤه إذا كان مختلفًا |
| `rejected` | رابط أو كود أو نمط سر محتمل أو طول غير مسموح | إعادة الصياغة دون تنفيذ أي مادة واردة |

التصنيفات المضافة هي `idea:submitted` و`idea:triage` و`idea:needs-info` و`idea:duplicate` و`idea:ready-for-review` و`idea:accepted` و`idea:rejected` و`idea:processed`. لا يضيف Workflow تصنيف `idea:accepted` ولا يقرر القبول؛ هذا قرار بشري.

## التحقق والتصفية

تقرأ `automation/triage_idea.py` نص القضية كبيانات فقط. لا تستورد النص إلى Python أو JavaScript قابل للتنفيذ، ولا تستدعي أي رابط وارد، ولا تكتب إلى backlog. ترفض الأداة أنماط مفاتيح شائعة، وروابط HTTP(S)، وعناصر HTML الحساسة، وواجهات الشبكة، والقضايا التي تتجاوز الحدود المحددة للحقول.

يتم تطبيع النص العربي للمقارنة، ثم تستخدم الأداة تشابه العنوان والوصف مع الأفكار الموجودة في `ideas/backlog.json`. إذا تجاوز التشابه عتبة حتمية، تصبح الحالة `duplicate`. لا تعتمد الأداة على التصويت وحده ولا تمنح الاعتماد النهائي تلقائيًا.

## ترتيب الأولويات

الدرجة الأولية من 100 نقطة، وهي اقتراح للمراجع وليست قرارًا آليًا:

| المعيار | النقاط |
|---|---:|
| وضوح المشكلة والعنوان والوصف | 20 |
| وضوح الجمهور | 15 |
| قوة دليل الحاجة | 20 |
| قابلية التنفيذ | 20 |
| الجِدّة مقارنة بالbacklog | 15 |
| السلامة | 10 |

يُقترح `template:converter` أو `template:text-tool` أو `template:visual-toy` للأشكال المعروفة، بينما تستخدم الأشكال الأخرى `generate`. لا يُستخدم هذا الاقتراح لتجاوز بوابات المرحلة 5 أو لإجبار النشر.

## Workflow والصلاحيات

يستجيب `.github/workflows/phase-7-idea-intake.yml` لحدثي `opened` و`edited` للقضايا الموسومة كأفكار، ويوفر تشغيلًا يدويًا برقم قضية. يملك `contents: read` و`issues: write` فقط. يجلب JSON القضية، يشغل الفرز، يحدّث تعليقًا واحدًا بعلامة ثابتة، يحدّث تصنيف الحالة، ويرسل Telegram. لا يملك صلاحية `contents: write`، ولا يتضمن `git push`، ولا يبني أو ينشر منتجات.

إذا فشل التشغيل، يُكتب تعليق فشل ويُرسل إشعار Telegram، مع النص الصريح بأن backlog لم يتغير ولم يُنشر منتج. لا تُطبع مفاتيح أو أجسام أسرار في السجل.

## معايير الإغلاق

تُغلق المرحلة بعد تحقق نموذج Issue Form من الهاتف، وفحص قضية صحيحة، وقضية ناقصة، وقضية مكررة، وقضية تحتوي رابطًا أو نمط سر، ونجاح تشغيل GitHub حقيقي يعلق النتيجة ويطبق التصنيف ويرسل Telegram. يجب أن يبقى `ideas/backlog.json` دون تغيير بعد التشغيل، ويجب أن يظل Pages والمنتجات الحالية دون تعديل. بعدها يُحدّث README وسجل الاختبار، ولا تبدأ المرحلة 8.
